АВТОСПОРТ — V1 WINDOWS PAPER / MARKET LAB

1. Запустіть Autosport.exe. Canonical Windows shell працює через Microsoft Edge WebView2 Runtime; якщо runtime недоступний, Autosport показує native Windows error і не переходить на старий Tk/ttk shell.
2. Для historical replay кнопка «Вибрати dataset» відкриває папку replay dataset, що містить manifest.json, market.jsonl і окремий sealed results.json. У packaged demo це папка examples\tt_demo.
3. У полі «Стратегія» виберіть canonical replay strategy. baseline-v1 працює без research plan; observe-only-v1 є no-action control; research-replay-v1 запускає typed research pipeline.
4. Для research-replay-v1 натисніть «Вибрати research plan» і виберіть causal JSON plan. У packaged demo готовий перевірюваний файл: examples\tt_demo\research_plan.json. Невалідний або відсутній plan відхиляється fail-closed до economic replay.
5. Після перевірки dataset, strategy і за потреби research plan натисніть «Запустити paper replay».
6. За замовчуванням replay використовує подієвий режим — максимально швидке causal відтворення без штучного очікування між котируваннями. Доступні також 1x, 10x, 100x і 1000x.
7. Для read-only live observation виберіть режим «Public preview — без ключа» або «API key з environment» і натисніть «Оновити live snapshot».
8. Authenticated live режим читає ключ тільки зі змінної середовища AUTOSPORT_PARLAYAPI_KEY. Ключ не вводиться в інтерфейс і не зберігається у workspace.
9. Canonical operator UI — semantic HTML у pywebview з explicit EdgeChromium/WebView2 backend. Live acquisition і economic replay виконуються поза WebView2 UI; JavaScript не володіє money/risk/settlement/execution/science authority.
10. Ctrl+O — поле шляху dataset; Ctrl+E — поле evidence export; Ctrl+L — live snapshot; F2 — навігація поверхнями; F8 — Evaluation. PAPER replay і recovery доступні як native HTML buttons через Tab + Enter/Space. F6/F7/F9/F10 та browser refresh chords не перехоплюються Autosport і залишаються WebView2/browser/assistive technology. Native HTML button/input/select/textarea/list semantics задають names/roles/states для WebView2 accessibility tree.
11. Віртуальний банк, рішення, market history, source health та run summaries зберігаються у локальному Autosport workspace і відновлюються після перезапуску. Economic history різних strategy/plan identities ізольована у strategy-specific workspaces.

PORTABLE DATA / RESEARCH TOOLS

12. У цій самій папці ZIP є Autosport-Data.exe — console tool, доступний з Windows Terminal / PowerShell і придатний для клавіатурної роботи та читання stdout screen reader-ом. Команда довідки: .\Autosport-Data.exe --help
13. Перевірити dataset без replay: .\Autosport-Data.exe verify-dataset .\examples\tt_demo
14. Команда acquire запускає canonical authenticated historical acquisition bundle: .\Autosport-Data.exe acquire --help. Вона читає AUTOSPORT_PARLAYAPI_KEY тільки з environment і не записує секрет у bundle. Отриманий bundle є acquisition evidence, а НЕ доказом licensing/retention, complete historical coverage, sealed settlement outcomes чи profitability.
15. Команда build-corpus запускає fail-closed canonical corpus assembly: .\Autosport-Data.exe build-corpus --help. Вона вимагає окремі sealed outcomes і зовнішній governance proof; без них replay-ready historical corpus не оголошується.
16. Для bundle, створеного командою acquire, використовуйте canonical adapter: .\Autosport-Data.exe build-corpus-from-bundle --help. Adapter перевіряє bundle identity і bound evidence перед передачею у той самий corpus assembler; opaque provider result rows не перетворюються автоматично на sealed outcomes.
17. Autosport-Data.exe не виконує реальні ставки і не містить bookmaker execution/funding/withdrawal path.

WALK-FORWARD EVALUATION

18. Для strict causal walk-forward evaluation відкрийте PowerShell у папці програми та виконайте: .\Autosport-Data.exe walk-forward-evaluate <evaluation-bundle.json> --output walk-forward-report.json. Команда використовує canonical evaluator і fail-closed temporal/cohort checks. Наявність report не є доказом profitability або predictive superiority; реальний OOS proof вимагає lawful governed historical corpus та чесного holdout/walk-forward protocol.

STRATEGY COMPARISON

19. Для fail-closed порівняння двох або більше completed strategy run summaries на тому самому sealed dataset відкрийте PowerShell у папці програми та виконайте: .\Autosport-Data.exe compare-strategies <run-summary-1.json> <run-summary-2.json> --baseline-strategy baseline-v1 --output strategy-comparison.json. Команда приймає лише сумісні canonical run summaries і записує machine-readable report; observed paper ordering не є доказом profitability, predictive superiority або out-of-sample переваги.

CRASH / ECONOMIC WORKSPACE RECOVERY

20. Якщо Autosport після аварійного завершення повідомляє про unresolved economic transaction, не видаляйте paper_book.json, decisions.jsonl, run_registry.json або transaction files вручну. Закрийте Autosport.exe, відкрийте PowerShell у папці програми та запустіть canonical fail-closed recovery для відповідного workspace: .\Autosport-Data.exe repair-workspace --workspace "<повний шлях до workspace>".
21. Для baseline-v1 типовий workspace показується безпосередньо в рядку «Віртуальний банк» GUI. Для інших strategy/plan identities використовуйте саме strategy-specific workspace, який GUI також показує під час replay. Команда recovery не запускається паралельно з active economic writer.
22. repair-workspace не «позначає run успішним» за припущенням. Вона завершує або відхиляє лише той стан, який може бути доведений canonical transaction/base hashes; неоднозначний стан залишається unresolved і повертає ненульовий exit code. Після успішного repair перезапустіть Autosport.exe і повторно відкрийте той самий strategy/plan context.

PHYSICAL WINDOWS 11 + NVDA ACCEPTANCE — HUMAN-ONLY RELEASE GATE

23. Цей розділ виконується людиною на фізичному Windows 11 з реально запущеним NVDA. Machine UIA/keyboard audit не замінює цей gate. ДО відкриття або тестування локального ZIP отримайте з незалежного GitHub Actions/control record для exact candidate два trust anchors: canonical source SHA та опублікований SHA-256 release ZIP. Не використовуйте BUILD_INFO або сам локальний ZIP як джерело «expected» значень. Окремо обчисліть SHA-256 локального ZIP і переконайтеся, що він точно дорівнює опублікованому digest; після fresh extraction також звірте BUILD_INFO `source_sha` з незалежно отриманим canonical source SHA та зафіксуйте `autosport_exe_sha256`. Будь-яка невідповідність = STOP/FAIL, цей build не тестуйте. Не змішуйте файли з іншого build.
24. Запустіть NVDA, після цього `Autosport.exe` лише клавіатурою. PASS вимагає, щоб NVDA озвучив зрозумілу назву головного вікна та початковий фокус; не можна використовувати мишу для обходу недоступного control.
25. Пройдіть Tab і Shift+Tab по primary flow. Зафіксуйте PASS лише якщо NVDA стабільно оголошує назву/роль/поточний стан для dataset control, strategy combobox, research-plan control, replay control, live mode/live refresh і status surface; фокус не повинен губитися або потрапляти в keyboard trap.
26. Натисніть Ctrl+O, виберіть packaged `examples\tt_demo`, виберіть `baseline-v1`, дійдіть Tab до native кнопки «Запустити PAPER replay» і активуйте її Enter або Space. PASS вимагає, щоб зміна стану replay та завершення/помилка були доступні NVDA без візуального читання екрана.
27. Через поле «Екран» і кнопку «Перейти до робочої поверхні» перевірте `paper tickets`, `live quotes`, `Evaluation і portfolio evidence`, економічні межі та ручні розрахунки. Кожна поверхня повинна отримувати передбачуваний фокус; NVDA має озвучувати заголовок/контекст, expanded/collapsed state для disclosures і доступний вміст або коректний empty state. Браузерні F6/F7/F9/F10 залишаються доступними WebView2/assistive technology.
28. Перевірте error path без підміни успіхом: спробуйте запустити `research-replay-v1` без research plan. PASS вимагає fail-closed поведінку до economic replay та доступне NVDA повідомлення про причину; silent failure або лише візуальна помилка = FAIL.
29. Завершіть Autosport.exe, запустіть його знову і поверніться до того самого strategy/workspace context. PASS вимагає доступного NVDA статусу після restart і відсутності втрати/підміни persistent economic state. Якщо програма повідомляє unresolved transaction, використайте тільки canonical `repair-workspace` flow з пунктів 20–22 і зафіксуйте фактичний результат.
30. Human acceptance evidence має містити: незалежно отримані canonical source SHA та expected release ZIP SHA-256, фактично обчислений SHA-256 протестованого ZIP, BUILD_INFO `source_sha`, `autosport_exe_sha256`, Windows edition/build, NVDA version, дату/час тесту, tester identity або відповідальний label, PASS/FAIL для пунктів 24–29 і дослівний опис кожного defect. Expected і фактичні candidate values мають точно збігатися. Будь-який required FAIL або identity mismatch залишає `HUMAN_TESTED=false`, `NVDA_VERIFIED=false` і `V1_READY=false` для цього candidate.
31. Лише окреме physical evidence, яке однозначно посилається на той самий exact packaged candidate, проходить незалежну source/package identity binding і має PASS для всіх required пунктів, може бути підставою для зовнішнього release decision. Сам packaged BUILD_INFO навмисно залишається `human_tested=false` і `nvda_verified=false`; build pipeline або ZIP не можуть самі собі приписати human proof чи бути єдиним джерелом expected identity.
32. Щоб не переплутати build під час фізичного тесту, створіть exact-candidate evidence template з незмінного release ZIP, передаючи trust anchors, які ви вже отримали незалежно від ZIP: .\Autosport-Data.exe nvda-evidence-template --release-zip "<шлях до Autosport-V1-windows-x64.zip>" --expected-source-sha "<canonical GitHub source SHA>" --expected-package-sha256 "<опублікований SHA-256 release ZIP>" --output nvda-acceptance.json. Команда fail-closed відхиляє ZIP, якщо його фактичний digest або BUILD_INFO source SHA не збігаються з цими anchors; вона фіксує exact candidate identity, але залишає всі людські поля незаповненими та всі truth flags false.
33. Після фактичного проходження пунктів 24–29 заповніть у nvda-acceptance.json Windows edition/build, NVDA version, timezone-aware tested_at, tester_label і для кожного check статус PASS або FAIL. Для FAIL обов’язково запишіть конкретний defect у notes; не змінюйте `human_tested`, `nvda_verified` або `v1_ready` у самому evidence-файлі.
34. Перевірте прив’язку evidence до того самого release ZIP, повторно використовуючи ті самі незалежно отримані trust anchors: .\Autosport-Data.exe verify-nvda-evidence --release-zip "<шлях до Autosport-V1-windows-x64.zip>" --expected-source-sha "<canonical GitHub source SHA>" --expected-package-sha256 "<опублікований SHA-256 release ZIP>" --evidence nvda-acceptance.json --output nvda-evidence-validation.json. Ця команда перевіряє структуру, повноту required checks, external source/package anchor binding та exact ZIP/source/exe identity; вона не може машинно довести, що фізичний NVDA-тест справді відбувся, не змінює BUILD_INFO і не виставляє `NVDA_VERIFIED=true`.

Live observation є read-only. Paper/replay функції використовують лише віртуальний банк. Програма не виконує реальні грошові ставки і не має механізму керування букмекерським рахунком, поповнення або виведення коштів.

Machine accessibility/keyboard audits є prerequisite evidence і не означають physical NVDA speech verification.
