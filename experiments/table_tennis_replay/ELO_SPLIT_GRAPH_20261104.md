# Залежність джерельних ID при розділенні зразка Elo за датою

Це дослідницький аналіз уже переглянутого зразка з 2 000 рядків, а не незалежний holdout, навчання чи оцінка моделі. [Межу аналізу](https://github.com/Oleksii-debug/Autosport/issues/2591#issuecomment-6640726565) опубліковано до нових підрахунків; діапазон дат та інші властивості зразка на той час уже були відомі. Дату `2026-10-01` обрано після перегляду діапазону, а не як заздалегідь невидимий період.

## Джерело і метод

Використано ті самі байти зразка видавця [lathise2025/table-tennis-elo-dataset](https://github.com/lathise2025/table-tennis-elo-dataset/tree/9eba2ade435ce27b4f3dcbd5aafc6bfbcd52d534), commit `9eba2ade435ce27b4f3dcbd5aafc6bfbcd52d534`, Git blob `14ce8e632c027432309c2decd672686d8b306c16`, SHA-256 `bbb2ab531f269a1eafff89e240086a4d17999114b582825ba4338986c6770fde`. Видавець зазначає [CC BY 4.0 для зразка та документації](https://github.com/lathise2025/table-tennis-elo-dataset/blob/9eba2ade435ce27b4f3dcbd5aafc6bfbcd52d534/LICENSE); право видавця на дані первинних провайдерів незалежно не перевірено. Весь платний набір не отримували. Видавець описує ID як стабільні, а рейтинги — як передматчеві; фізичні особи та час їх створення чи доступності не засвідчені.

Умовне розділення використовує **лише мітки дат**: рання частина — дати строго до `2026-10-01`, пізня — на цю дату або після неї. Імена, ймовірності моделі, Elo, результати та рахунки не використовуються для побудови поділу, перетинів або графа. Наявна `elo_sample_inventory.audit`, яку новий код повторно використовує для перевірки хешу й структури всього CSV, також читає та підраховує коректність інших полів; ці підрахунки в показники нижче не входять.

Порівняно два простори **точних рядків**: глобальний `player_id` у межах цього файлу та пара `(точна мітка змагання, player_id)`. Другий підхід не вважає однаковий ID у двох різних мітках однією сутністю; перший з'єднує їх лише за джерельним рядком. Жоден не підтверджує особи чи географії. Кожний рядок утворює ребро між своїми двома ключами; окремо підраховано зв'язні компоненти й повтори неорієнтованої пари в ранній частині.

**Граф побудовано на всіх рядках, включно з пізніми.** Тому він є ретроспективним описом структури вибірки, а не ознакою, яку можна було використовувати до пізніших записів. Компонента, що перетинає межу, може зв'язувати рядки через ланцюжок спільних ключів; це не означає, що кожен її рядок має прямий збіг в іншій частині.

## Агрегати

Рання частина має **1 696 рядків**, пізня — **304**. Різних точних ID матчів у попередній інвентаризації було 2 000, проте різні ID не доводять різних фізичних матчів.

| Показник | Глобальний точний ID | Точна пара змагання–ID |
| --- | ---: | ---: |
| Різні ключі ранньої / пізньої частини | 1 223 / 452 | 1 229 / 452 |
| Ключі, наявні в обох частинах | 359 | 354 |
| Пізні рядки з 0 / 1 / 2 ранніми ключами | 20 / 67 / 217 | 24 / 65 / 215 |
| Пізні рядки з тією самою неорієнтованою парою в ранній частині | 46 | 46 |
| Зв'язні компоненти всього | 118 | 129 |
| Найбільша компонента: рядки / ключі | 645 / 262 | 645 / 262 |
| Компоненти з рядками по обидва боки межі | 26 | 25 |
| Ранні / пізні рядки в таких компонентах | 1 587 / 288 | 1 583 / 284 |

Повторення учасників між минулим і майбутнім **саме по собі не доводить витоку**: дослідження повторюваних гравців може правомірно використовувати їхню історію, якщо кожен запис був доступний до рішення і тестові події відокремлені належним чином. Окрема перевірка на нових для навчання учасниках ставить інше питання. Ці підрахунки допомагають розрізнити такі постановки, але не засвідчують незалежності або достовірної хронології жодної з них. Порядок усередині дня, час матчу, факт і час публікації результату, права й відповідність ID реальним особам лишаються невідомими.

## Перевірка та відтворення

Основний [код](elo_split_graph_audit.py) застосовує union-find. Окремий [контроль](elo_split_graph_reference.py) використовує обхід графа в ширину й незалежний підрахунок перетинів. Всі показники збіглися на однакових перевірених байтах; обидва алгоритми використовують **той самий парсер і те саме джерело**, тому не є незалежною перевіркою джерельної істини. Синтетичні тести включають перестановку сторін і рядків, з'єднання компонент пізнішим ребром, різні простори ключів, межу дати, відсутні/повторні ID, зміну даних про рахунок/модель, незмінність виходу, запуск CLI і 200 згенерованих графів. Контрольні [основний](elo_split_graph_20261104.json) та [незалежний](elo_split_graph_reference_20261104.json) агрегати не містять окремих ID; перевірено точну рівність їхніх текстових значень із 3 289 різними рядками джерельних match/player ID, збігів немає. Це не загальна гарантія анонімності.

```sh
PYTHONPATH=src:experiments/table_tennis_replay python experiments/table_tennis_replay/elo_split_graph_audit.py SAMPLE_CSV OUTPUT_JSON --expected-sha256 bbb2ab531f269a1eafff89e240086a4d17999114b582825ba4338986c6770fde --cutoff-date 2026-10-01
PYTHONPATH=src:experiments/table_tennis_replay python experiments/table_tennis_replay/elo_split_graph_reference.py SAMPLE_CSV REFERENCE_JSON --expected-sha256 bbb2ab531f269a1eafff89e240086a4d17999114b582825ba4338986c6770fde --cutoff-date 2026-10-01
```

Вихідні файли створюються лише за відсутності попередніх. Локально Linux/Python 3.12 пройшли **522 тести**, з них **16 нових**; три нові Python-файли пройшли `compileall`. Усі 512 наявних Python-файлів дослідницької директорії та `src/autosport` збіглися з батьківським GitHub head; три Python-файли — нові. Сім додаткових канонічних тестів і `tests/conftest.py` також збіглися. Статус CI точного GitHub head зазначено окремо в issue. Нових цін або результатів не запитували; модель не навчалася, фактична прибутковість не оцінювалася, ставок не зроблено.
