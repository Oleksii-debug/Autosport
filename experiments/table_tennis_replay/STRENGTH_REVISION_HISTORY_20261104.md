# Історія виправлень для замороженої форми та H2H — 4 листопада 2026

Це продовження [попереднього порівняння](FROZEN_STRENGTH_COMPARISON_20261104.md) та [протоколу](https://github.com/Oleksii-debug/Autosport/issues/2591#issuecomment-6638174559). Дослідницький адаптер зіставляє **записані** послідовні відповіді результатів із тими самими замороженими оцінками. Навчання, ставки, підтвердження прибутковості або незалежний форвардний експеримент не виконувалися.

## Що змінено

`causal_strength_revision_history` повторно використовує наявні `causal_strength_frozen.evaluate`, перевірку датованої відповіді та автомат станів `causal_h2h_revision_history`. У відповідь із кожною квитанцією входять три окремі когорти після карантину: ринок на всіх придатних результатах; ринок і форма на тих самих придатних ID з формою; ринок, форма та форма+H2H на тих самих ID з обома ознаками. Для кожної когорти задано кількість, ID та Brier/log loss. Порожня когорта дає `null`. `source_scorer_counts` описує придатність цієї окремої відповіді **до** перевірки попередніх виправлень; `counts` і когорти — після неї. ID у звіті є джерельними і потребують приватного зберігання, якщо вихідні дані непублічні.

Якщо раніше придатний запис зник, став непридатним чи змінив зміст, він потрапляє в стійкий карантин, навіть якщо згодом джерело поверне попередню версію. Непридатний запис зі статусом `finished`, який пізніше стає придатним, також карантиниться, зокрема після проміжної відсутності. Раніше відсутній або незавершений результат може стати придатним лише під час пізнішого отримання; зміна лише `updated_at` не є зміною спортивного змісту. Раніші знімки звіту не перезаписуються.

Це консервативні **стани роботи з записами**, а не висновки, що фізичний матч чи офіційний результат змінився. Наприклад, [документація джерела](https://moviodds.com/doc) описує резервний режим `memory`, в якому старі результати можуть бути відсутні, і `finished_at` як останнє спостереження live-матчу. Зникнення рядка тому залишається причиною карантину, а не доказом зміни результату. Відповіді про різні дати, непридатна послідовність запитів або змінені байти відхиляються.

Нове посилання ланцюга `research.tt_result_history_link.v2` містить SHA-256 прогнозу **та** його часової квитанції, SHA-256 відповіді результату та її квитанції, послідовність і хеш попереднього посилання. Скоринг вимагає обидва окремо закріплені хеші прогнозу й останній хеш ланцюга. Формат старого ринкового журналу `v1` збережено; v1/v2 взаємно не підміняються. Неповний запис після збою відхиляється й потребує перевірки, не виправляється автоматично. Підтримується до 256 квитанцій і один процес запису; конкурентний запис не кваліфіковано.

Цілісність відносна до наданих хешів. Код не доводить, що їх закріплено незалежно **до** результату, що наданий кінець ланцюга найновіший, що не було незаписаних відповідей чи виправлень, а годинники, джерело, особи, права й ринкові ціни є достовірними. Вхідні сховища й сирі відповіді треба зберігати приватно та відповідно до прав. Також потрібні окремий протокол, фактичні підтверджені джерела та незалежний holdout перед висновками про якість; формули залишаються фіксованими ілюстративними евристиками без калібрування.

## Синтетичні перевірки і старий архів

У повністю **синтетичному** прикладі на першій квитанції є 3 придатні результати: форма доступна на 2 ID, форма+H2H — на 1. На другій один результат змінюється, ще один зникає; залишається 1 придатний і 2 карантинні ID. Третя відповідь повертає початкові значення, але карантин зберігається; форма оцінюється на одному ID, а H2H-когорта порожня. Тести також перевіряють Brier/log loss на однакових ID, зміну рахунку без зміни переможця, невчасне оновлення, виправлення після непридатного `finished`, перехід з `unknown`, повний запуск CLI, підміну кожної частини, пропущену ланку, відкат head, частковий запис, переприв'язку хешу квитанції й несумісність версій.

Для перевірки сумісності повторно прочитано **вже відомий** приватний [архів трьох відповідей](https://drive.google.com/file/d/1NSHnM1cCF9VAiEMwMM9RgJurybmAjYL6/view) з локально збереженої копії; контрольний запис для відтворення — [попередній звіт](RESULT_REVISION_HISTORY_20261030.md). У локально доступній копії всі 26 записів маніфесту збіглися за довжиною та SHA-256; нова v1-реалізація повернула структурно ідентичний раніше збереженому JSON звіт. Кількості придатних за трьома відповідями: **1, 11, 11**, карантинних — нуль. Це перевірка сумісності на тих самих уже відомих відповідях, не нові спостереження і не незалежний тест моделі. Журнал з 11 оцінками мав порожній реєстр ідентичності, тому для нього не створювали прогнозів форми/H2H заднім числом. Імена, ID та сирі відповіді не опубліковано.

Окрема **пост-хок** перевірка ідентичності в цій локальній копії: всі 11 ID прогнозів знайдено у першій відповіді цін, а `home` і `away` у всіх 11 — рядки. У цих рядках та відповідних рядках трьох результатів (1, 11 і 11) жоден не містить на верхньому рівні жодного з полів `home_id`, `away_id`, `homeId`, `awayId`, `home_player_id`, `away_player_id`, `home_participant_id`, `away_participant_id`, `player_id`, `participant_id`. Це лише перевірка перелічених назв полів на верхньому рівні, не доказ відсутності будь-якого ID в інших полях і не звірення особи. У трьох збережених відповідях позначено `source=postgres`; це самозвіт постачальника, не незалежне підтвердження повноти чи достовірності архіву.

## Запуск

Після окремого створення і попередньої фіксації прогнозу, його квитанції та протоколу:

```sh
# Порожня наявна директорія HISTORY, лише один процес запису.
PYTHONPATH=src:experiments/table_tennis_replay python experiments/table_tennis_replay/causal_strength_revision_history.py append ROOT HISTORY BODY RECEIPT --expected-forecast-sha256 FORECAST_SHA --expected-forecast-receipt-sha256 FORECAST_RECEIPT_SHA
# Незалежно зберегти отриманий latest_link_sha256; для наступної відповіді
# додати --expected-head LATEST_LINK_SHA і знову незалежно зберегти новий head.
PYTHONPATH=src:experiments/table_tennis_replay python experiments/table_tennis_replay/causal_strength_revision_history.py score ROOT HISTORY OUTPUT --expected-head LATEST_LINK_SHA --expected-forecast-sha256 FORECAST_SHA --expected-forecast-receipt-sha256 FORECAST_RECEIPT_SHA
```

Локальна перевірка Linux/Python 3.12: 471 тест пройшов, включно з 17 новими; `compileall` для змінених/нових Python-файлів пройшов. Перед публікацією 506 із 507 Python-файлів у дослідницькій директорії та `src/autosport` збіглися з батьківським GitHub head; єдина відмінність — навмисно змінений журнал. Два нові Python-файли ще не були на head. Чотири окремі канонічні тести й `tests/conftest.py` також побайтово збіглися з head. Це не GitHub CI, не тест на Windows і не перевірка джерельної істини.
