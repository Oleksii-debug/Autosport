# Однакові рядки прогнозу і джерельні кандидати — 5 листопада 2026

## Питання і межі

У [попередньому аудиті](EXTERNAL_ELO_CAUSALITY_20261105.md) в опублікованому
CSV прогнозів знайдено два рядки з однаковими значеннями всіх 25 полів;
сам CSV не має ID матчу. Цей окремий ретроспективний крок перевіряє, скільки
записів опублікованого видавцем Parquet можуть відповідати такій групі.
[Протокол](https://github.com/Oleksii-debug/Autosport/issues/2591#issuecomment-6646749800)
зафіксовано до декодування Parquet і перевірки рядків. Це не новий holdout,
не навчання й не перевірка фінансового результату.

Джерело — commit [topspin-lab `ebe19dd52f0b`](https://github.com/Roni-quant/topspin-lab/tree/ebe19dd52f0bf6e7353f1fa5442afd2d5e361e40).

## Результат

У Parquet **857** рядків. Усі 857 пройшли видимий у
[`validate_london_2026.py`](https://github.com/Roni-quant/topspin-lab/blob/ebe19dd52f0bf6e7353f1fa5442afd2d5e361e40/experiments/validate_london_2026.py#L122)
структурний фільтр: `drop_reason` відсутній, `is_doubles` — false; точні
ключі для цього обмеженого порівняння структурно придатні. Це не перевірка
подальшого фільтра cold-start чи відтворення історичних ознак.

У групі з **двох однакових прогнозних рядків** знайдено **два** записи
Parquet з тією самою впорядкованою четвіркою точних джерельних ключів:
учасник A, учасник B, переможець, категорія. Обидва записи мають зазначені
`source_match_id` і `match_key`; кожне з цих двох полів має **два різні
значення**, пропусків і повторів усередині цієї пари немає.

Це важливе уточнення: однакові рядки прогнозу **сумісні з двома різними
джерельними записами**. Однак у CSV немає поля, яке зв'язує конкретний
прогноз із конкретним Parquet-рядком; порівняння дає групу з двох кандидатів,
а не доведений зв'язок 1:1. Різні `source_match_id` не доводять двох
фізичних матчів, а `match_key` — [похідний хеш видавця](https://github.com/Roni-quant/topspin-lab/blob/ebe19dd52f0bf6e7353f1fa5442afd2d5e361e40/experiments/fetch_london_2026.py#L81),
не незалежний офіційний ідентифікатор. Особи, вихідні записи ITTF та
первинна істинність не звірені. Жодного рядка не зливали й не вилучали.

Зіставлення не використовує схожість імен, реальні часи, турнірні назви як
ідентичність чи оцінку якості прогнозів. Воно не перевіряє, чи CSV створено
саме з цих байтів, чи був прогноз заморожений до матчу, чи були результати
доступні в потрібний момент. Права на первинні дані, ринкові котирування,
прийняття ціни й прибутковість залишаються невідомими.

## Як перевірено байти

У середовищі не було встановлено `pyarrow` або іншого стандартного
Python-читача Parquet. Для SNAPPY-файлу використано окрему локальну копію
MIT-проєкту [hyparquet](https://github.com/hyparam/hyparquet/tree/a32933592707c833780f9cdacc2529c3b68a41d0),
commit `a32933592707c833780f9cdacc2529c3b68a41d0`, версія 1.32.0. Перед
імпортом декодер звіряє [маніфест 30 Git blobs](hyparquet_reader_manifest_20261105.json)
читача і SHA-256 Parquet; декодує рівно вісім потрібних колонок із тих самих
перевірених байтів. Це перевірка відповідності зафіксованому коду читача,
не незалежне підтвердження правильності декодування. Іншого Parquet-читача
в цьому прогоні не було.

Тимчасове приватне подання восьми колонок мало SHA-256
`d0b4080bf79ab6e225e53846470fd9e5d2d9521ce81953959a10029ebb74bd61`.
Воно містило source-local ID і не включене до GitHub; після розрахунку
вхідні CSV, Parquet і це подання видалено з тимчасового каталогу. Публічний
[агрегат](topspin_duplicate_source_candidates_20261105.json) містить лише
лічильники. Хеш тимчасового подання не є підписом видавця та самостійно не
доводить правильності транскодування.

Окремий квадратичний підрахунок на тих самих декодованих байтах відтворив
`2 прогнозні рядки / 2 кандидати / 2 різні source ID / 2 різні match_key`.
Він незалежний від алгоритму групування основного адаптера, але не від
Parquet-декодера, даних видавця чи їхнього походження.

## Відтворення

Локально отримайте вказані вище файли видавця і точний commit hyparquet із
збереженими шляхами. Декодер створює файл із source ID лише за відсутності
шляху та з режимом доступу `0600`; тримайте його приватно. На Linux із Node
24 та Python 3.12:

```sh
node experiments/table_tennis_replay/decode_topspin_parquet.mjs \
  hyparquet_dir london_2026_matches.parquet private-transcode.json
PYTHONPATH=src:experiments/table_tennis_replay python \
  experiments/table_tennis_replay/topspin_duplicate_source_candidates.py \
  london_2026_predictions.csv private-transcode.json aggregate.json \
  --expected-csv-sha256 9bcaa521b50cc573195545094c54601fa8f071b017ea8ed2e8498f076f80b983 \
  --expected-transcode-sha256 d0b4080bf79ab6e225e53846470fd9e5d2d9521ce81953959a10029ebb74bd61
python experiments/table_tennis_replay/topspin_duplicate_source_reference.py \
  london_2026_predictions.csv private-transcode.json
```

Адаптер повторно використовує `prediction_inventory` з попереднього аудиту,
строгий JSON-парсер і точне зіставлення source-local ключів. Вхідний
`transcode_sha256` прив'язує лише надані локальні байти, не засвідчує їх
від видавця; `reader_commit` у JSON сам по собі також не є атестацією.
Без оригінального Parquet й перевіреного читача стверджувати побайтове
походження транскодування не можна.

На Linux/Python 3.12 пройшли **572 тести**, з них **11 нових**. Обидва
опційні тести із закріпленими зовнішніми вихідними файлами та локальним
Parquet-читачем були ввімкнені й фактично виконані. Перевірено 0/1/кілька
кандидатів, відсутні/повторні ID, перестановку сторін, відхилені записи,
пошкоджені хеші та підміну файлу читача до імпорту. `compileall` і
`node --check` пройшли. Із наявних Python-файлів дослідницького каталогу,
`src/autosport` і шести канонічних наборів із `conftest.py` **532** збіглися
з батьківським GitHub tree `2bc98d5dc28b725c3a88d465394787f7714d033e`;
три Python-файли нові. Статус hosted CI точного коміту — окремо в issue.
